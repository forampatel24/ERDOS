# DATA_PIPELINE.md

# Data Pipeline Documentation

**Project:** Explainable Real-Time Emergency Disaster Orchestration System (ERDOS)

**Version:** 1.0

---

# 1. Purpose

This document describes how data flows throughout the entire system, from the moment it is collected until it reaches the emergency commander dashboard.

The pipeline follows an **event-driven, stream-first architecture**, where every incoming event updates a live Digital Twin of the disaster environment. AI models operate on this continuously updated state to generate predictions, which are then transformed into operational decisions and explainable recommendations.

This document does **not** describe implementation details. Instead, it explains the movement of data between different system components.

---

# 2. Pipeline Philosophy

The system processes four categories of data:

- Static Data
- Historical Data
- Live Data
- Simulated Data

Each category serves a different purpose.

| Data Type | Purpose |
|-----------|----------|
| Static | Build the Digital Twin |
| Historical | Train AI models |
| Live | Update the Digital Twin |
| Simulated | Emulate unavailable operational events |

# 7. Simulation Pipeline

Certain operational events are unavailable as public real-time data.

These events are generated by the Simulation Engine.

## Simulated Events

- IoT water sensors
- Rain sensors
- Emergency calls
- Rescue requests
- Ambulance locations
- Boat locations
- Shelter occupancy
- Traffic updates
- Road failures

## Flow

```text
Simulation Engine

↓

Generated Event

↓

Kafka Producer

↓

Kafka
```

The simulator complements live data and enables realistic disaster scenarios.

# 8. Apache Kafka Pipeline

Kafka acts as the central event streaming platform.

It transports events between producers and consumers.

Kafka does not process data.

Kafka does not perform analytics.

Kafka only distributes events.

## Producers

- Weather Producer
- River Producer
- Simulator Producer

## Consumers

- Apache Flink

# 10. Apache Flink Pipeline

Apache Flink processes incoming event streams.

Responsibilities:

- Event aggregation
- Sliding windows
- Stream processing
- Feature calculation

Example

Incoming events:

```text
2:00 PM

Rain = 20 mm
```

```text
2:05 PM

Rain = 32 mm
```

```text
2:10 PM

Rain = 58 mm
```

Flink computes:

```text
Rainfall during last 10 minutes

58 mm
```

instead of treating each event independently.

---

# 11. Feature Engineering Pipeline

The Prediction Layer never consumes raw sensor data.

Instead, Flink generates meaningful features.

Examples

Weather

↓

Rainfall Rate

Rainfall Accumulation

Rainfall Trend

River

↓

Water Rise Rate

Water Level Difference

Water Velocity

Road

↓

Elevation

Distance to River

Traffic Density

Flood History

Neighbour Flood Status

These engineered features are forwarded to the Digital Twin.

---

# 12. Digital Twin Update Pipeline

The Digital Twin State Manager maintains the current virtual state of Kerala.

Every incoming feature updates one or more entities.

Example

Before

```text
Road R27

Rain = 20 mm

Water = 0.08 m

Status = SAFE
```

After

```text
Road R27

Rain = 61 mm

Water = 0.43 m

Status = WARNING
```

The Digital Twin always reflects the latest available information.

It acts as the single source of truth for the entire platform.

---

# 13. Prediction Pipeline

The updated Digital Twin becomes the input to the Prediction Layer.

Two independent models operate simultaneously.

## Model 1

Road Flood Prediction

Algorithm

- XGBoost

Predicts

- Flood probability
- Road accessibility

---

## Model 2

Flood Propagation Prediction

Algorithm

- ST-GNN

Framework

- PyTorch Geometric

Predicts

- Future spread of flooding
- Infrastructure impact

---

The outputs of both models together represent the predicted future state of the Digital Twin.

---

# 14. Orchestration Pipeline

The Orchestration Engine converts predictions into operational recommendations.

Inputs

- Current Digital Twin
- Flood Predictions
- Propagation Predictions
- Resource Availability
- Shelter Status

Responsibilities

- Shelter Selection
- Safe Route Planning
- Ambulance Allocation
- Rescue Boat Allocation
- Resource Scheduling

The engine uses optimization and graph algorithms to compute the best solution.

---

# 15. Decision Validation Pipeline

The environment changes continuously.

Previously generated plans may become unsafe.

The Decision Validation Engine continuously evaluates active recommendations.

Example

Current Route

↓

Road R27

↓

Shelter A

Five minutes later

Road R27 flood probability increases to 91%.

The engine detects that the route is no longer safe.

A new plan is automatically generated.

---

# 16. Explainability Pipeline

Every prediction and every operational recommendation is accompanied by an explanation.

Techniques

- Captum
- Treelite

Outputs

- Feature Importance
- Decision Paths
- Structured Explanation Object

Example

```text
Road R27

Flood Probability = 91%

Primary Factors

• Heavy Rainfall

• Rising Water Level

• Low Elevation
```

---

# 17. Natural Language Pipeline

The Structured Explanation Object is forwarded to an external LLM API.

Purpose

Convert structured evidence into concise operational language.

Example

Input

```json
{
  "decision":"Evacuate Shelter B",
  "reason":[
    "Road R27 flood probability 91%",
    "Water level rising",
    "Low elevation"
  ]
}
```

Output

> The evacuation route has been updated because Road R27 is predicted to become inaccessible due to rapidly rising floodwaters. Shelter B remains safely accessible and has sufficient capacity.

The LLM never performs prediction, optimization, or decision making.
